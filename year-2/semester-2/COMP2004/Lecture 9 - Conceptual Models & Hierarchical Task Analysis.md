
## Mental models

Mental models are internal representations of external processes. **It is the way users understand and expect the system to work.** For example, a mechanic has an engineering-oriented mental model, whereas a driver has a different model.

There should be a principle of transparency that aid the user in constructing a mental model. 


## Conceptual models
These are higher-level descriptions of how a system should be organised, be working, and operate.

it uses internal and external cognitive perspectives. This means we use the knowledge the user has already in their head and in the world. 

Designers need to discover the user’s mental model, and make a conceptual model. Then, designers develop the system, which users evaluate.

This can be done by using metaphors for real life. For example, ”add to card” and the recycle bin. When users see this icon, they know they can drag and drop icons to the bin to remove them.


### Gulfs of execution and evaluations

Consider what the user wants to do. To achieve the goal, the system may help them easily, then everything is okay. If there are difficulties, there is a gap between the user and the system, which creates a gulf. 

If the system does not give feedback such as “this file has been deleted”, it can create confusion and a gap. If the system does not allow the user to delete something, versus allowing the user to do it easily, then the gap widens. A good design tries its best to bridge this gap by having loops of design to check if the design is as convenient as they need. 

## Hierarchical task analysis
If there is a goal the user wants to achieve, an easy way to do it, we can break it down into smaller tasks and sub-tasks, that makes it easier for designers to check and evaluate whether the users e.g. spend too much time on a task, or have to reiterate multiple steps needlessly without a result.

It can be done to improve an existing or in-design system. 

It generates a hierarchical model of tasks (high level, user-oriented tasks at the top, low-level system-oriented tasks at the bottom).

It helps to identify the steps users take to achieve goals, while conceptual models ensure the system’s structure and functionality matches the steps. 

For example, to send an email:
- Click on “new email”
- Edit the message
	- Enter the name
	- Enter subject
	- Enter text
- Send message

### Performing an HTA
All HTA requires it breaking the main goal into a series of many sub-tasks. 

Different users have different preferences (can be done with personas - hypothetical characters). There can be many different scenarios - first-time users requiring signing up, versus repeat users who sign in. 

The HTA has to have a defined scope of analysis, with an initial flowchart.

We must keep in mind and document:
- the frequency of each task;
- the time to complete each task
- difficulty of each task (mental load, skills required) 
	- requires the user to memorise codes/passwords is not easy, or possibly it requires a technical skill (e.g. coding)
- criticality of each task (essential vs optional)

We collect data to understand what the users do: 
- observe/interview users, tell user to think aloud whilst they are doing a task, check system logs (what steps were done, decision when using it)

This data can be represented with
- tables
- diagrams (trees, piecharts)

This should be presented to the user to refine the process. Discussing with the user is important to resolve/understand any misunderstandings, and discussions with designers to identify consequences is important too.
