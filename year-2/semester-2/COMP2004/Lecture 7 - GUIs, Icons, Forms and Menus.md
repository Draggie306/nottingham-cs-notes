
## Icons
It is useful feedback that, when selected, it changes colour: highlighted, increases brightness, etc., to distinguish it from nearby, unselected icons. 

Icons should stand out from the background. They should have suitable contrast but not look too odd. Additionally, movement. The properties of the object should be there: a recycle bin takes references from real life, and real offices containing files and folders. 

Icons should be harmonised: they should all have a consistent colour, outlining, etc., when presented and grouped together. 

## Dialogue boxes
Allow users to take action, select options, fields/menus, etc.

The natural flow (sequencing) is top left to bottom right. It is small enough not to obscure the background, with clear options to complete/move next and cancel. 

It is best to have one column, versus two columns that cause the user to be distracted. 

### Forms 

Forms should be given a meaningful title, and sections within a form should be meaningfully **grouped** and subtitled - allowing each section to jump out, and clear where each section has is boundaries, begins and ends.

Instructions should be short but intuitive. Field types and labels should be familiar - the way data is inputted matters (e.g. for a date of birth) versus a simple text field.

Error correction for characters and fields, especially for things like passwords:
- Instead of showing a red border, it can show more information with *why* something is wrong. 
- A completion signal: some websites may show a set of rules, and as each of these are met, the rule text turns green or shows a tick.
- If something is not necessary for the user, it is not necessary to show it: the user can become overwhelmed 

### Error messages
Even if the user follows the steps, we may need to inform the user that there is an error.

They should be:
- explicit
- human-readable
- polite
- concise
- constructive

The user should be told clearly how to resolve it, what they can do to progress, and what caused this error in an easy to understand manner (avoid intimidating words like illegal). An error code could be shown instead, allowing for technical support to provide assistance.

If the user did not enter a specific field, instead of saying “field was not entered”, write “please complete this field”. The position could be shown near to the error source, in a consistent place, or a dialogue box on the centre of the screen. 

Repair mechanisms can give the user a sense of agency and control, such as undo/redo buttons. These might not always be feasible but should be attempted.

## Menus

Ideally, there should be no more than 3/4 levels - otherwise the navigation slows down, with the user losing themselves in the hierarchy. Having too many (breadth) items per level can lead to scanning problems - the user may have already forgotten what’s come first. There should be no more than 8 items per level. 

A bottom bar can be used with common features.

### Mobile device navigation

Burger menus are built when we are concerned about space, such as on mobile devices. Users may miss it, unless the menu is floating, but it may block the content behind. It also does not reveal what it contains.

Having a top tab menu on mobile is inconvenient: the thumb cannot reach it easily. Integrating gesture-based navigation is important.
