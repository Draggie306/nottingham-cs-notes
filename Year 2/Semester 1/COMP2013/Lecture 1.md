Y1 modules - Intro to Software Engineering

Software maintenance is central to software development: it involves **maintainable software** and **software maintenance**. The goal of this module is to ensure we can write maintainable code.


In most software engineering jobs, you will:
- Join a team, working on existing software
- Be assigned a ticket on something like Jira
- Comprehend why a part of a big project is not working/needs changing
- Propose a fix to a manager
- Fix, test, document, and merge a fix
- Improve the fix based on code review feedback
- Leave the software in a better place than when it was found.

Being agile means to be agile about how agile works. It means being agile about the infrastructure, how the team works, how the testing works: this is more **DevOps** than Agile.

This module is about how to approach a large mass of code, and tools to maintain it without breaking other parts in a collaborative manner.

The module works with bigger projects in Java. Projects will be big so that it is difficult to understand, complex, with scope for additions. 


Maintainable software is:
- Modular: there are discrete components; changes to one component has minimal impact on others (low ripple effect)
- Reusable: one bit of code is reusable in different places, and in new software.
- Analysable: becomes easy to say what each bit does together.
- Modifiable: it is clear how code should change without introducing defects
- Testable: each bit of code can be tested individually.


There are 3 principles for developing maintainable software:
1. It benefits from adhering to simple guidelines
	1. e.g. never write methods >15 lines
2. It is not an afterthought, but should be addressed from the start of a project
	1. but also applies to all changes
3. Some violations are worse than others; the more it adheres the more maintainable it is

The biggest part about software development is maintenance.

There are 3 types of maintenance:
- Corrective maintenance: finding and fixing errors  (2/3 of all types)
- Adaptive maintenance: adapting to changes in the environment - e.g. new Windows version, a library is no longer available (this happens in coursework)
- Perfective + preventive maintenance: stakeholder has changed requirements, better to restructure now than bolt-on to existing (most expensive)

Most of the work in this module is **understanding the existing code** and **refactoring the existing code**. Fixing a problem requires in-depth knowledge of the “crime scene” - where did the crime take place, who committed it and what else was involved.

Part of making software is making diagrams - simpler UML is easier than complex UML. 

> It’s impressive to create a huge program with complex looking diagrams, but the real test of maintainability is being able to simplify that.
